## Run one question

Configure `.env` using the existing portable model settings and `BERN_DATA_DIR`. The answer client requires a compatible server supporting chat completions with JSON Schema response formatting. It does not install model weights, assume a particular GPU, or start/stop any service.

From the repository directory:

```bash
uv run --locked python -m core.answer_cli \
  "According to I.1, what is the place called?" \
  --transcription-id 16 \
  --data-dir data/derived/j2-full \
  --out runs/j3-location-01
```

Then exercise natural-language retrieval without a survey code:

```bash
uv run --locked python -m core.answer_cli \
  "What is the name of the place where the school is located?" \
  --transcription-id 16 \
  --data-dir data/derived/j2-full \
  --out runs/j3-natural-location-02
```

The explicit-code command already returned a correct development answer citing record 41; keep its existing output folder rather than rerun into it. The revised natural-language command uses a new folder, preserving the failed `j3-natural-location-01`. Its success is not established yet. Explicit codes are derived from the literal user request and checked against the dataset catalogue, not a hardcoded answer ID. Code-only requests without a transcription ask for scope instead of picking an arbitrary dossier.

Each `--out` must be new. On failure, retain that folder and choose another name. Omitting `--out` creates a unique folder under `runs/answers/`. Run records are refused inside source/dataset directories. Input files and existing runs are never overwritten. The command exits nonzero for technical errors; a legitimate insufficient-evidence response is a completed request, not a process failure.

## Behavior and limits

- Search and filtering use the existing CPU index. If literal search fails within a selected transcription, one bounded model request selects up to three actual catalogue question codes only; no unused query strings are requested or accepted. An empty code list yields insufficient evidence. For archive-wide search, the plan retains up to three catalogue codes and three keyword queries, with the same eight-word/160-character query validator. The caller's scope is retained; model routing hypotheses are not evidence.
- Evidence contains at most five distinct within-transcription text groups, 2,000 characters per passage and 11,000 serialized packet characters. Source IDs and quality flags are retained; other candidates and truncation are recorded. These are **character limits, not exact tokenizer qualification**. The full model request has an 18,000-character guard; the server enforces its actual context limit. An over-context/unsupported-format response is a technical error, not a valid answer.
- One answer generation requests up to 512 tokens. One shared answer-validation retry is allowed; retrieval planning has no retry. Maximum three generation POST attempts, no transport retry, warmup, model switching or agent loop. Normal stops and exact response model identity are required; truncation is an error.
- Every claim needs an ID in the delivered packet and an exact quote in the delivered original span. Software attaches citations and original source cards; model metadata is not trusted. These checks **do not establish semantic entailment**.
- Repeated text is grouped only within the same transcription; separate sources are not collapsed. Grouping does not alter the source exports. School IDs/raw assignment numbers are explicitly unresolved context, and affected answered responses carry a software warning. The model is instructed to make transcription-level claims; this is not an automatic semantic school-attribution proof.
- Missing evidence returns `insufficient_evidence`, never a claim that information is absent everywhere. Model/data/validation failures return `error`. Both return `answer: null`. No stale or demonstration answer is substituted.
- Model output does not rewrite scholarly text or infer pages, currency conversions or archive-wide statistics. Archival text is packaged as untrusted data; the model is given no tools. Model prompt-injection resistance remains an empirical evaluation question.

## Output and integration

The CLI prints the existing five-field `AnswerResponse`: `mode`, `status`, `answer`, `sources`, `message`. Each source card retains the original six source fields in `contracts.py`.

The UI uses the unchanged function:

```python
from core.service import answer_question

response = answer_question("According to I.1, what is the place called?", 16)
```

This is an execution example, not something imported automatically. `core.service.search_records` remains independent of the model. The answer function creates a unique run directory automatically; the CLI also prints its exact path. Neither interface calls a hardcoded infrastructure host.

Run artifacts are `input.json`, `implementation.json`, `dataset.json`, `retrieved_sources.json`, `evidence.json`, `response.json`, `summary.json`, and, when used, `serving.json`, `models.json`, `retrieval_plan.json`, `validated_claims.json`, `events.jsonl`. Module/prompt hashes bind the implementation. Wire events preserve actual request bodies, raw responses, normal/error finishes and durations before parsing. No authorization header/API key is recorded. Failed raw replies remain. Mock transports are explicitly labelled `mock_transport`, not actual inference.
