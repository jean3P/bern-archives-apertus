# J4: evaluation and reviewer-bound scoring

**Opt-in hybrid candidate:** [HYBRID.md](HYBRID.md) documents the new Qwen32B interpretation/extraction and Apertus8B final-answer path. Select `--pipeline qwen-apertus`; the default `apertus` path is retained. Hybrid software controls, serving and acquisition are not executed in this implementation handoff. Its maximum is four POSTs/one shared retry per question, while the baseline remains three. Saved review records and the original reference bundle are unchanged. The coverage-only implementation described below is the preceding candidate, not a new hybrid result.

J4 evaluates a frozen backend candidate without changing it during the batch. The original development run is preserved, and M1's live UI is merged. A generic question-coverage correction is now implemented on `jean/evaluation`, but **this candidate and its new software controls have not been executed**. Run the software tests before acquiring revised model replies. The prior merged-base test result does not qualify this changed candidate.

## Inputs and boundaries

- A completed, unchanged J2 dataset, such as `data/derived/j2-full`. The runner verifies it; it does not rebuild it or execute SQL.
- The hashed reference snapshot in `evaluation/references/draft-v1`: 20 development questions, 30 evaluation questions and a separate 100-transcription audit selection.
- The existing model connection in the ignored `.env`. No particular GPU or host is required by this runner.
- A **new output directory** for every acquisition or scoring operation.

Only `question` and `transcription_id` enter `run_answer`. Expected facts, source IDs, quotes and labels stay evaluator-only. The same full archive is searched: separate reference dossiers are not proof that the model or archive has never seen those documents.

The draft references were source-checked, not human-approved. `--allow-draft-references` explicitly labels a diagnostic; it does not turn the draft into gold. Alternatively, after a person actually reviews the exact snapshot, `--reviewed-by` records that person's attestation. It is not a substitute for doing the review. Do not edit expected answers after seeing model outputs. Prepare a new version for any legitimate reference correction.

## Question coverage candidate

One correction covers both retrieval and generation, without another model stage or a changed response schema:

- Natural-language questions receive one bounded routing request covering every requested facet, even if a literal search could match only one part. The route still chooses up to three catalogue codes; global queries retain the existing word/character bounds. Literal search is a fallback when routed retrieval produces no cards. Explicit-code requests and `--no-query-rewrite` retain their diagnostic behavior.
- The answer instructions require requested details, original terms, exceptions and meaning-changing qualifiers in the actual claim text, not only in quotations. They ask the model to check all delivered passages before abstaining.
- Requested arithmetic may use explicit compatible operands, with the operands and derived result stated and cited. Missing operands, overlapping counts, unsupported conversions and invented historical frequencies remain disallowed. No arithmetic engine or case-specific answer substitution is added.

The three-generation-POST cap, one shared answer-validation retry, 180/512-token generation limits, evidence limits, exact-quote validator, model client and evaluator are unchanged. Previously successful literal-only queries may now require a routing call; measure the call and latency change rather than assuming a speedup.

`implementation.json` labels the candidate `cited-answer-v2-question-coverage` and binds both router prompts and the answer prompt by hash. Runtime code does not read evaluation references or contain expected development answers/IDs. Prompt instructions and valid quotes do **not** automatically certify semantic completeness or arithmetic correctness. The new controls use synthetic source text and mock replies, not a new measured model result.

Preserve the original `runs/j4-development-01`. Review all 20 revised replies against its results, not only the five failures: complete-question correctness, false abstentions, unsupported additions, source coverage, calls/retries and timings. Do not copy the original review bindings to new replies or infer semantic success from automatic metrics. Use a different fresh output name if the proposed directory already exists. This is a development comparison, not independent validation.

Use the CLI for this comparison: it loads the new source in a fresh process. An already-running UI can retain imported older code until a deliberate restart; it is not part of this source-only handoff. No model-server restart is required by the correction.

For the separate 30-case evaluation, first review the reference questions, required facts, original terms, forbidden inferences and nonanswer reasons. Only **after that review**, use the actual reviewer's name:

```bash
uv run --locked python -m core.evaluate_cli run \
  --references evaluation/references/draft-v1 \
  --split evaluation \
  --data-dir data/derived/j2-full \
  --out runs/j4-evaluation-01 \
  --reviewed-by "Jean Pool Pereyra Principe"
```

Each acquisition is sequential, with no evaluator-level inference retry. J3 retains at most three generation POST attempts and one answer-validation retry per question: at most **60 development / 90 evaluation / 150 combined POST attempts**, not guaranteed usage. Model-list GET requests are separate. Actual attempts, validation retries and returned token usage are recorded. A caught backend interruption or receipt/budget guard stops further acquisition; unstarted cases stay in the scheduled denominator. Normal backend `error` replies remain failed cases, not historical absence.

The runner does not start, restart or stop a model server. It adds no warmups, model changes or test-time tuning. Source/data-completion changes invalidate the batch. A preparation failure leaves `_FAILED.json`; never reuse that directory. A recorded batch has `_COMPLETE.json` even when its state is `aborted`: inspect its state and counts, not just marker existence. Exit code 2 indicates incomplete/technically failed acquisition, not a semantic quality verdict.

## Output records

| File | Meaning |
| --- | --- |
| `run-manifest.json`, `dataset-verification.json` | Ordered cases, reference review status, code/data hashes, model connection/settings and limits; no API key |
| `code-snapshot/`, `references/` | Exact evaluated backend and reference files, including uncommitted source bytes |
| `cases/<case_id>/` | Unchanged J3 input, retrieved cards, evidence, raw requests/replies, validated claims, response and timings |
| `observation-<case_id>.json`, `score-<case_id>.json` | Durable wrapper result and mechanical inspection for each scheduled case |
| `case-observations.jsonl`, `case-scores.jsonl` | Consolidated acquisition and scoring rows; failures are retained |
| `review-template.jsonl` | Pending question-level meaning/support decisions, bound to each response |
| `document-review-template.jsonl`, `document-scores.jsonl` | Separate 100-record projection audit, initially all pending |
| `metrics.json`, `report.md`, `_COMPLETE.json` | Mechanical metrics, reviewed results if supplied, limitations and file integrity hashes |

`reference_hit_at_5` asks whether a known supporting ID and quote occur in the first five cards. `all_reference_spans_delivered` checks all known reference spans in the actual packet. Neither establishes semantic correctness. Scoped duplicate-source alternatives are allowed only for their declared case/reference; an identical short word under another survey question is not interchangeable evidence.

## Human review and offline scoring

Keep acquired runs immutable. Copy the templates **outside** the original run, then edit only those copies:

```bash
cp runs/j4-evaluation-01/review-template.jsonl runs/j4-evaluation-review-01.jsonl
cp runs/j4-evaluation-01/document-review-template.jsonl runs/j4-document-review-01.jsonl
```

For each question, compare the final response with the reference's required meaning and the actual delivered sources. Keep `case_id` and `review_binding` unchanged. Fill `reviewer`, `decision` (`correct`, `incorrect`, `uncertain`, or null while pending), `supported_claims` (0 through the actual claim count) and `notes`. A `correct` answer must cover every required fact without unsupported additions; review every generated claim, not just the expected one. Mechanical quote validity is not entailment. Nonanswers require an appropriate scoped explanation; an empty packet does not demonstrate answer-model abstention over nonempty evidence. Technical failures cannot be marked correct.

For document review, compare the **whole** public dossier and associated answers against the independent original source: exact text/nulls, identities, joins, metadata, locator and excluded fields. Keep its ID, stratum and binding unchanged. Fill reviewer, `correct_projection`, `structural_error` and concrete notes. Both decisions must be boolean together or both null while pending. Preserved uncertainty, null text and editorial markup are not themselves errors. Do not certify a dossier from a single matching sentence or from the derived index alone.

After review, compute scores from saved receipts only:

```bash
uv run --locked python -m core.evaluate_cli score \
  --run runs/j4-evaluation-01 \
  --reviews runs/j4-evaluation-review-01.jsonl \
  --document-reviews runs/j4-document-review-01.jsonl \
  --out runs/j4-evaluation-scored-01
```

Omit either review option if that review is not ready. The scorer makes no model or retrieval calls, copies submitted decisions, validates response bindings and writes a new sealed directory. Duplicate, stale or unknown case reviews are rejected. Original runs, references and model replies are never overwritten.

## Interpreting results

- Question accuracy stays **null until every scheduled case has a verdict**. Confirmed failures, pending reviews and uncertain decisions stay visible. A fully reviewed, interrupted batch retains unstarted cases as failures of that scheduled procedure; report coverage alongside accuracy.
- Automatic metrics cover status, contract/quote checks, known-reference retrieval/coverage, attempts, retries and recorded latency. Meaning and citation support require review. A frozen software fixture is labelled `software_fixture`, never actual inference.
- Document accuracy uses the actual reviewed-document denominator and reports pending coverage. For 100 fully audited transcriptions, at least 80 correct and at most four structural-error records meet the declared sample targets. This is **not an official 80% chatbot threshold** or a corpus-representativeness claim.
- First and subsequent application-request timings are separated; model startup and device memory are **unmeasured**, not zero. The run does not establish laptop suitability or physical-page throughput.
- Thirty evaluation questions concern six reference dossiers. After using their results to choose a fix, a rerun is a regression comparison, not fresh independent validation.

J4 closes only after actual acquisition, independent review/audit and a saved failure analysis. Implemented files or passing software tests alone do not close it.
